# API contracts: current and proposed

## Current FastAPI contract — implemented adapter
Source: Freesia-backend main 53dfc2d (2026-10-02 local integration), app/main.py, app/schemas.py and app/routers. All routes below are relative to /api. Default Vite proxy preserves /api and forwards to localhost:8000/api. A direct VITE_API_BASE_URL must also include /api. Production routing must preserve the same prefix; the Vite development proxy is not part of the build.
- GET /infra-spaces, GET /infra-spaces/{id}: persisted seeded foundations, fields id/name/description/network/computes/deployable_computes/app_count. network ha is backend literal, not proof of private or Multi AZ topology.
- GET/POST /repositories and DELETE /repositories/{id}: SQLAlchemy-backed URL registrations; branch defaults to main. POST returns201, DELETE204 without JSON; errors409 duplicate,422 validation,404 missing. No GitHub existence/public/branch check yet.
- GET/POST /app-spaces, GET /app-spaces/{id}. POST name/repo_url/branch/infra_id. IDs must come from API foundation list, never local source-generated designs.
- POST/GET /app-spaces/{id}/analysis: requirements/evidence/candidates/mascot_message. Candidates selected/alternative/unsuitable remain server recommendation; user selection is separate.
- POST /app-spaces/{id}/deployments: {compute,plan_id?}; backend validates plan_id existence, matching app and compute; compute_not_ready400 and deployment_in_progress409 are explicit errors. Frontend new-deployment UI requires a reviewed server plan. GET /deployments/{id}; GET /deployments/{id}/resources returns address/type/action/state/reason/updated_at. GET /deployments/{id}/events emits progress status/step/message/progress/url/at; preserve native EventSource reconnect, close only terminal/malformed/dispose. First connection returns the latest persisted event; Last-Event-ID reconnect replays newer events.
- Structured errors {error,message}, 400/404/422/500. NonJSON/connection/schema failures become visible errors; no demo fallback.
- App/deployment/events/resources now persist in the database. Analysis is persisted and the route now invokes the AI module in the background when AI_MODEL_ID is configured; without a model it returns a sample done result. DEPLOY_SIMULATE=true and no AI_MODEL_ID are explicit in local runtime. No verified real cloud/workflow dispatch. /api/health is platform backend health only.

## Current UI meeting flow — local DEMO only
Main destinations: Infra / Application / Integration. All demo screens are accessible without a role switch; this is not authentication/RBAC.
- Infra flow correction approved 2026-10-01: create Space with name only -> Q&A including region -> Terraform generation/review -> explicit Apply demo -> progress/result in the same Space. New Space creation does not require choosing a fixed presentation template. The UI uses declared sample/structured answers, not a real LLM.
- `draft` is a new Space still gathering answers; `source_generated` means unbuilt code. `demo_deployed` means only a browser foundation sample eligible for the local application demo. Neither state proves real provider resources or is sent to backend as provisioned. Three original sample foundation IDs remain stable for old v1 app records.
- Current Infra Terraform is a fixed VPC/Subnet draft plus optional public route/gateway. DB isolation, Bastion, VPC Gateway Endpoint, ALB, ECS Cluster, IAM, NAT and full working deployment are not generated/validated/applied. Template metadata is an explanation, not discovered AWS state.
- Integration directly registers an existing GitHub HTTPS repository URL in the browser demo, with main implicit for new entries. There is no account connection/OAuth UI. Normalize trailing slash/.git; reject malformed URLs and duplicate URL+main (case-insensitive repository identity). Registered entries alone appear in app creation. Repository/public/main availability is unverified; no GitHub or backend request occurs. Unregistering removes eligibility for new apps, not existing apps. Legacy registrations/branches are retained.
- New App Space chooses a registered repository and named Infra Space. New repository registrations use main; historical registered branches remain intact. There is no Repository URL input in Application, including API mode.
- Deploy click displays fixed code evidence, mascot, read-only branching explanation and eligible candidate cards. Server/sample recommendation and user selection remain separate. Unsuitable or unsupported candidates are excluded rather than used as filler.
- Selected compute loads a template+values plan set. Demo plans are declared browser samples; API plans use POST/GET /app-spaces/{id}/plans (implemented in backend53dfc2d). Normal response contains one done plan using template default values. Display that plan directly without a selection button, retaining values review and explicit deployment; older multi-plan responses remain selectable. API404/501 still cannot start a deployment.
- New demo runs store the selected template/values and use six stages: queued / prepare / build / deploy / verify / done. There is no simulated user-repository Terraform commit/push. Timers only advance clearly labeled DEMO progress; real API progress comes exclusively from server events.
- Build failure simulation remains available. Explicit retry creates another demo run with its reviewed plan. Old saved code-based seven-stage demo records remain readable/resumable for storage compatibility; they are not used for new plans.
- API mode supports real repository list/register/unregister and app creation using the selected server repository URL/branch and server Infra ID. Repository loading/error/retry are visible; late async results after navigation/source change are ignored. Local demo repositories are never submitted. Infra create/provision remains unsupported; no fake route or automatic fallback. Analysis can be real or sample depending on server model configuration. Deployment/events/resources are persisted server records and locally simulated in this test runtime, not evidence of AWS deployment.
- Logs/metrics remain fixed local samples; API unsupported. Backend `/api/health` is platform health, not customer application health.

## Local persistence and boundaries
Versioned localStorage key `freesia.demo.v1` retains existing designs/apps/deployments and optional meeting metadata (Infra Spaces, sample connection, registered repo IDs). Optional demo pipeline lives on the existing Deployment; no parallel shadow pipeline store.
Previously saved standalone designs remain preserved as legacy unbuilt records and are excluded from ready foundations. New conversation, generated code and demo Apply outcome belong to the same Infra Space. Free text is retained but not analyzed by a real AI. Changing answers invalidates previous code and Apply result; saving code alone is not readiness.
Invalid stores, unknown template keys and malformed pipeline metadata produce a visible error and are not overwritten silently. Reset is explicit. Space/app drafts survive main navigation/source changes. Creation/start persistence errors retain the draft/preview. API lifecycle never writes demo IDs into local storage. Async results are scoped to selected app/navigation generation and discarded after Back, mode change or unmount.

## PROPOSED backend contracts — discussion only, NOT implemented calls
1. Repository registration: ADR-011 confirmed no user OAuth. API spec section5 (draft) plans GET/POST/DELETE /api/repositories for public URL registration, branch defaults to main. Frontend supports browser demo and server CRUD as of 2026-10-02. Actual GitHub repository/branch validation remains future backend work. App create continues repo_url+branch+infra_id per current schema, repository_id is future additive work. Tokens belong on backend, not browser.
2. Infra AI conversation/session: Space ID, initial requirement, message/answer history and pending questions -> generated Terraform files/version, assumptions, unsupported requirements and validation outcome. The confirmed answers and reviewed code version must accompany Apply; stale code must never execute. These are proposed contracts, not implemented backend routes.
3. Infrastructure deployment/reconciliation: explicit operation and authorization, statuses `source_generated / validating / provisioning / provisioned / failed`, real provider outputs and runtime capabilities. Only verified `provisioned` records can become real app targets. `demo_deployed` must never be accepted as provider readiness.
4. Application analyze/recommend: actual repo revision/evidence, compatible candidates and read-only decision explanation. User choice does not overwrite recommendation. Latest option B selects prebuilt workload-deploy/templates plus values; it does not generate/push Terraform into the user repository.
5. Deployment workflow dispatch: backend must validate selected plan_id/template/values and dispatch the deployment workflow; its signed plan retrieval belongs to the workflow, never the frontend. Never mark actual deployment successful from a frontend timer. Idempotency and production retry behavior require backend agreement.
6. Logs/metrics/alerts/customer healthcheck and authentication remain absent and require separate contracts. App plan routes are implemented as of53dfc2d with explicit error handling; no monitoring or Infra mutation route is invented.

Latest user clarification: 2-3 recommendation comparison belongs only to Application analysis/deployment. Infra directly generates Terraform after Q&A. This supersedes the earlier Infra recommendation interpretation.

## Deployment completion update — 2026-10-02
- Analysis and plan pending/running results poll GET every2seconds after a single POST, with a60second deadline including in-flight requests. Cancel/back/source change/unmount aborts the browser request/wait; it is not a backend task cancellation API.
- Application detail uses ?app=<id>&source=api|demo for reload restoration. GET deployment plus the latest SSE event restores current progress; GET need not duplicate step/progress. Missing old event history stays unprovided rather than inferred from status.
- Six visible stages follow server step identifiers. Transport errors keep EventSource automatic reconnect; malformed events show errors and stop the stream. Failure reason is recovered from deployment GET.
- Resources render actual reported address/type/action/state/reason/update time, grouped by type. No dependency edges, invented resources or synthetic percentages are inferred. Empty, loading, unsupported and failed states are distinct; refresh on deployment events or explicit retry.
- Plans support status/compute/plans[], each id/name/summary/pros/cons/template/values. Frontend display is read-only; compute must match the user's selection and plan_id must come from the loaded plan set. Backend validation and real workflow dispatch remain required.
- Old private/ha and proposed multi-az/db-isolated network values are accepted without implying unreported AWS topology.
- Local backend DB and previous in-memory app/deployment snapshots were backed up before migration0002; existing4apps/2deployments were restored. Explicit local resource fixtures are test data, not AWS observations.
